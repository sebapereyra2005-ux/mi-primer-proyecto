================================================================================
1. PRODUCTO Y PROPUESTA DE VALOR
================================================================================

La capa más importante. El 80% de las apps que mueren no fallan por falta de
features ni por bugs: fallan porque nadie entiende para qué sirven o nadie
las necesitaba lo suficiente.


1.1 CLARIDAD DE PROPUESTA
[  ] Una frase de menos de 15 palabras que explique qué hace y para quién
     -- Si no se entiende en 5 segundos, ya perdiste al usuario
     -- Test: muéstrasela a alguien fuera del equipo, ¿la repite igual?
[  ] Visible en la home / landing en el primer scroll
[  ] Coherente en App Store / web / redes sociales
[  ] Sin jerga técnica (a menos que el público sea técnico)


1.2 FOCO EN UN SOLO TRABAJO PRINCIPAL
[  ] La app hace UNA cosa excelentemente bien
     -- Las apps que hacen 10 cosas, hacen 10 cosas mediocre
[  ] Las features secundarias no compiten visualmente con la principal
[  ] Cada feature nueva pasa el test: "¿hace mejor el trabajo principal
     o lo distrae?"
[  ] Lista pública de "lo que NO vamos a hacer"
     -- Es tan importante como lo que sí harás


1.3 TIEMPO AL PRIMER VALOR (TTFV)
[  ] El usuario obtiene algo útil en menos de 60 segundos desde el primer click
     -- "Útil" significa: completó la acción que vino a hacer
[  ] Sin tour de onboarding obligatorio
[  ] Sin login obligatorio en V1 (el login se gana, no se exige)
[  ] Sin formularios largos antes del valor
[  ] La primera pantalla muestra DIRECTAMENTE la acción principal


1.4 RAZÓN PARA VOLVER
[  ] Una razón clara para que el usuario abra la app mañana
     -- Sin retorno no hay producto, hay anécdota
[  ] La app acumula valor con uso (historial, datos, mejora personalizada)
[  ] Hooks de retorno legítimos (no manipulativos):
     - Recordatorios útiles que el usuario configuró
     - Datos que solo se generan si vuelve
     - Comunidad / contenido nuevo
[  ] Métrica de retención definida (D1, D7, D30)


1.5 MODELO DE NEGOCIO (SI APLICA)
[  ] Cómo se genera dinero está decidido antes de lanzar
[  ] Pricing simple — máximo 3 planes
[  ] Comparativa visual entre planes
[  ] Free tier que de valor real (no demo crippleado)
[  ] Trial sin tarjeta si es B2C
[  ] Cancelación con un click — sin "llama a un agente"
[  ] Política de reembolso clara
[  ] Recibos / facturas automáticos


1.6 INVESTIGACIÓN DE USUARIO
[  ] Hablaste con al menos 10 usuarios potenciales antes de codear
[  ] Tienes claro su "trabajo a hacer" (jobs-to-be-done)
[  ] Documentaste sus puntos de dolor reales (no asumidos)
[  ] Tienes 1-3 personas (perfiles) bien definidas
[  ] Sabes qué soluciones usan hoy y qué les falta


================================================================================
2. EXPERIENCIA DE USUARIO (UX)
================================================================================

La diferencia entre una app que se siente profesional y una que se siente
amateur está casi siempre en estos detalles, no en las features.


2.1 JERARQUÍA Y FOCO POR PANTALLA
[  ] UNA acción primaria por pantalla
     -- Si hay dos botones igual de prominentes, no hay foco
[  ] El resto de acciones visiblemente secundarias
     (botones ghost, links pequeños, menús)
[  ] La pantalla principal sin competencia visual
[  ] Sin notificaciones intrusivas en el primer uso
[  ] Sin pop-ups antes de que el usuario haga algo


2.2 LOS 4 ESTADOS DE CADA PANTALLA
La mayoría de las apps solo programan el "happy path" y se rompen en
producción. Cada pantalla con datos debe contemplar:

[  ] ESTADO VACÍO
     -- Primera vez del usuario, sin datos todavía
     -- Debe guiar qué hacer, no mostrar una pantalla blanca
     -- Incluye CTA para crear el primer dato
[  ] ESTADO DE CARGA
     -- Skeleton screens > spinners (cuando se puede)
     -- Feedback inmediato: el usuario no espera sin saber qué pasa
     -- Si tarda más de 3s, mostrar mensaje explicativo
[  ] ESTADO DE ERROR
     -- Mensajes humanos, no stack traces
     -- Siempre con una ruta de recuperación ("Reintentar", "Volver")
     -- Diferenciar errores de red, de servidor, de datos
[  ] ESTADO DE ÉXITO
     -- Confirmación visual de que la acción se completó
     -- Sin abusar de toasts gigantes


2.3 FEEDBACK INMEDIATO
[  ] Cada click responde en menos de 100ms
[  ] Estados hover, active, focus, disabled visibles
[  ] Botones cambian a "Cargando..." cuando procesan
[  ] Los formularios dan feedback en tiempo real (no solo al enviar)
[  ] Las acciones destructivas piden confirmación
[  ] Las acciones reversibles muestran "Deshacer" 5-10 segundos


2.4 ONBOARDING
[  ] Sin onboarding obligatorio — el primer click ya da valor
[  ] Si hay tour, debe ser saltable
[  ] Tooltips contextuales en lugar de tour separado
[  ] Empty states que enseñan al usar la app
[  ] Datos de ejemplo precargados (opcional)
[  ] Progressive disclosure: features avanzadas se revelan al usar


2.5 NAVEGACIÓN
[  ] El usuario siempre sabe dónde está
     (breadcrumbs, títulos de página, navegación destacada)
[  ] Botón de "volver" predecible
[  ] URLs limpias y compartibles
[  ] Deep linking funciona (compartir un link lleva al lugar exacto)
[  ] Gesto de "atrás" del navegador respeta el flujo
[  ] Atajos de teclado para usuarios power


2.6 INPUTS Y FORMULARIOS
[  ] Solo pides la info estrictamente necesaria
[  ] Validación inline (no esperar al submit)
[  ] Mensajes de error específicos ("Email inválido" no "Error")
[  ] Inputs con tipo correcto (email, tel, number, date)
[  ] Autocompletado donde tenga sentido (autocomplete="email")
[  ] Placeholders no reemplazan labels
[  ] Tab order lógico
[  ] Submit con Enter cuando aplique
[  ] Botón "guardar" desactivado mientras procesa
[  ] Auto-save cuando sea posible (no perder lo escrito)


2.7 MICROINTERACCIONES Y ANIMACIÓN
[  ] Transiciones sutiles entre pantallas (200-400ms)
[  ] Animaciones que comunican causa-efecto, no decorativas
[  ] Respetar prefers-reduced-motion del usuario
[  ] Sin parallax extremo, sin efectos que mareen
[  ] Cuando algo cambia en pantalla, no aparece bruscamente


2.8 COPYWRITING
[  ] Voz y tono coherente en toda la app
[  ] Botones con verbos claros ("Guardar", no "OK")
[  ] Errores escritos como humano (sin "Exception: invalid_input")
[  ] Confirmaciones específicas ("Nota guardada", no "Éxito")
[  ] Sin emojis salvo que pertenezcan a la marca
[  ] Sin signos de exclamación gratuitos
[  ] Mensajes vacíos motivan, no acusan ("Aún no tienes notas",
     no "No tienes nada")


================================================================================
3. DISEÑO VISUAL Y SISTEMA DE DISEÑO
================================================================================


3.1 SISTEMA DE DISEÑO
[  ] Paleta de colores definida y limitada
     -- Máximo 3 colores principales + escala de grises
     -- Cada color tiene un uso específico (primario, acento, error)
[  ] Escala tipográfica restrictiva (5-7 tamaños máximo)
[  ] Escala de spacing consistente (4px, 8px, 16px, 24px, 32px, 48px, 64px)
[  ] Escala de bordes redondeados (sm, md, lg, full)
[  ] Tokens de diseño documentados (Figma, Storybook, etc.)


3.2 COLOR
[  ] Color primario para acciones, no para decoración
[  ] Suficiente contraste de texto (mínimo WCAG AA, idealmente AAA)
[  ] Estados de los componentes diferenciados (hover, active, disabled)
[  ] Color no es la única forma de comunicar estado
     (también iconos, texto, posición)
[  ] No depender de daltonismo-sensibles (rojo/verde sin acompañamiento)
[  ] Modo oscuro y claro (si aplica), no solo invertir colores


3.3 TIPOGRAFÍA
[  ] Una sans-serif para texto general
[  ] Opcionalmente una mono para datos / código
[  ] Pesos limitados (regular, medium, semibold)
[  ] Line-height de 1.5 para texto largo
[  ] Letter-spacing apropiado (negativo en titulares grandes)
[  ] Tamaño mínimo de cuerpo: 16px
[  ] Línea entre 50-75 caracteres para lectura cómoda
[  ] Fuentes web cargadas eficientemente (preload, font-display: swap)


3.4 ICONOGRAFÍA
[  ] Una sola familia de iconos (Lucide, Heroicons, Phosphor, etc.)
[  ] Tamaños consistentes (16, 20, 24)
[  ] Stroke o fill consistente (no mezclar)
[  ] Iconos siempre con label o aria-label cuando son interactivos


3.5 IMÁGENES
[  ] Ratios consistentes (16:9, 4:3, 1:1)
[  ] Lazy loading para todas las imágenes below-the-fold
[  ] Formatos modernos (WebP, AVIF) con fallback
[  ] Tamaños responsive con srcset / sizes
[  ] Alt text descriptivo en todas las imágenes informativas
[  ] Alt vacío en imágenes decorativas (alt="")
[  ] Skeleton / blur placeholder mientras cargan


3.6 SOMBRAS Y PROFUNDIDAD
[  ] Escala limitada de sombras (sm, md, lg, xl)
[  ] Coherente: si una card tiene sombra, todas las cards similares también
[  ] En modo oscuro, las sombras se reemplazan por bordes


================================================================================
4. RESPONSIVE Y MULTI-DISPOSITIVO
================================================================================

Más del 60% del tráfico web es móvil. Una app que funciona mal en el teléfono
es una app que pierde a la mayoría de sus usuarios.


4.1 MOBILE-FIRST
[  ] Diseñas y desarrollas primero para mobile, luego escalas a desktop
[  ] La pantalla principal cabe en una vista de móvil sin scroll horizontal
[  ] Touch targets mínimos de 44x44px (Apple) / 48x48dp (Google)
[  ] Espaciado entre elementos clicables suficiente para dedos
[  ] Sin hover-only — todo accesible con tap


4.2 BREAKPOINTS COMUNES
[  ] Mobile: 320px - 640px
[  ] Tablet: 641px - 1024px
[  ] Desktop: 1025px - 1440px
[  ] Wide: 1441px+
[  ] Probado en cada breakpoint, no solo en uno


4.3 INTERACCIONES TÁCTILES
[  ] Sin elementos pegajosos en hover (no funcionan en touch)
[  ] Swipe gestures donde tengan sentido (eliminar, refrescar)
[  ] Pull-to-refresh en listas largas
[  ] Sin doble-tap para zoom (configurar viewport bien)


4.4 SAFE AREAS Y NOTCHES
[  ] Respetar safe-area-inset-* en iOS
[  ] viewport-fit=cover en index.html
[  ] Probado en dispositivos con notch (iPhone X+)


4.5 ORIENTACIÓN
[  ] Funciona en portrait y landscape
[  ] Si bloqueas una orientación, justificado (juego, lectura)


4.6 NAVEGADORES Y DISPOSITIVOS
[  ] Probado en Chrome, Safari, Firefox, Edge
[  ] Probado en iOS Safari (es distinto a Safari desktop)
[  ] Probado en Chrome Android
[  ] Probado en al menos un Android viejo (carga lenta)
[  ] Funciona en pantallas pequeñas (320px)
[  ] Soporta pantallas retina (imágenes 2x, 3x)


================================================================================
5. ACCESIBILIDAD (A11Y)
================================================================================

No es opcional. 1 de cada 5 personas tiene algún tipo de discapacidad. Y
además: lo que es bueno para a11y es bueno para todos los usuarios.

Estándar mínimo: WCAG 2.1 nivel AA.


5.1 SEMÁNTICA HTML
[  ] Usar elementos correctos: <button>, <a>, <nav>, <main>, <article>
[  ] No usar <div onClick> en lugar de <button>
[  ] Estructura de encabezados jerárquica (h1, h2, h3)
[  ] Una sola <h1> por página
[  ] Landmarks semánticos (<header>, <main>, <footer>, <nav>)


5.2 NAVEGACIÓN POR TECLADO
[  ] Toda funcionalidad accesible solo con teclado
[  ] Tab order lógico (sigue el flujo visual)
[  ] Focus visible siempre (outline o equivalente)
[  ] Atajos de teclado documentados
[  ] Esc cierra modales / dropdowns
[  ] Enter activa botones
[  ] Skip-link al contenido principal


5.3 LECTORES DE PANTALLA
[  ] aria-label en iconos sin texto
[  ] aria-live para contenido que cambia dinámicamente
[  ] aria-describedby para hints adicionales
[  ] role="alert" para errores críticos
[  ] aria-expanded en dropdowns
[  ] aria-current en navegación activa
[  ] Probado con VoiceOver (Mac/iOS) o NVDA (Windows)


5.4 CONTRASTE Y VISIÓN
[  ] Texto normal: contraste mínimo 4.5:1 con fondo
[  ] Texto grande (18pt+): contraste mínimo 3:1
[  ] Componentes UI y estados: contraste mínimo 3:1
[  ] No depender solo de color para comunicar (también texto/iconos)
[  ] Texto puede aumentar a 200% sin romper layout


5.5 MOVIMIENTO Y MEDIOS
[  ] Respetar prefers-reduced-motion
[  ] Sin auto-play de video con sonido
[  ] Sin elementos que parpadeen más de 3 veces por segundo
[  ] Captions en videos
[  ] Transcripts en audio


5.6 FORMULARIOS ACCESIBLES
[  ] Cada input con su <label> asociado
[  ] Errores asociados al input (aria-invalid, aria-describedby)
[  ] Required campos marcados también con texto, no solo asterisco
[  ] Instrucciones antes del input, no después

6. PERFORMANCE
================================================================================

Una app lenta pierde usuarios. Google ha demostrado que cada 100ms adicionales
de carga reducen las conversiones medibles.


6.1 CORE WEB VITALS
[  ] LCP (Largest Contentful Paint) < 2.5s
     -- Tiempo hasta que el contenido principal aparece
[  ] INP (Interaction to Next Paint) < 200ms
     -- Latencia de respuesta a las interacciones del usuario
[  ] CLS (Cumulative Layout Shift) < 0.1
     -- Cuánto se mueve el contenido durante la carga
[  ] TTFB (Time To First Byte) < 600ms


6.2 OPTIMIZACIÓN DE BUNDLE
[  ] Code splitting por ruta (lazy loading de páginas)
[  ] Tree shaking activo en producción
[  ] Bundle inicial menor a 200KB gzipped (objetivo)
[  ] Sin librerías duplicadas
[  ] Análisis del bundle (vite-bundle-visualizer, webpack-bundle-analyzer)
[  ] Polyfills solo para los navegadores que necesitan


6.3 IMÁGENES
[  ] Formato moderno (WebP/AVIF)
[  ] Tamaños responsive (srcset, sizes)
[  ] Lazy loading nativo (loading="lazy")
[  ] Dimensiones explicitas (width/height) para evitar CLS
[  ] CDN de imágenes (Cloudinary, imgix, Vercel Image Optimization)


6.4 FUENTES
[  ] font-display: swap para evitar texto invisible
[  ] Solo pesos que usas, no la familia completa
[  ] Subset de caracteres (latin, latin-ext) si aplica
[  ] Self-hosted o de proveedor confiable (Google Fonts, Bunny Fonts)
[  ] Preload de la fuente crítica


6.5 CACHING
[  ] Headers Cache-Control bien configurados
[  ] Assets con hash en el nombre (cache eterno)
[  ] HTML con cache corto + revalidate
[  ] Service Worker para offline (si PWA)
[  ] Versionado de assets para invalidación


6.6 RED Y SERVIDOR
[  ] HTTP/2 o HTTP/3 activo
[  ] Compresión Brotli o Gzip
[  ] CDN frente al origen (Cloudflare, Fastly, Vercel Edge)
[  ] Servidor cerca del usuario (multi-región si tienes tráfico global)
[  ] Connection pooling en backend


6.7 RUNTIME
[  ] Sin loops innecesarios en render
[  ] Memoización donde aplique (React.memo, useMemo, useCallback)
[  ] Virtualización de listas largas (>100 items)
[  ] Debounce / throttle en inputs y scroll
[  ] requestIdleCallback para tareas no críticas


6.8 MEDICIÓN CONTINUA
[  ] Lighthouse CI en pipelines
[  ] Real User Monitoring (RUM) en producción
[  ] Alertas si las métricas se degradan
[  ] Performance budget definido y enforced


================================================================================
7. ARQUITECTURA TÉCNICA
================================================================================


7.1 ESTRUCTURA DE CÓDIGO
[  ] Separación clara de responsabilidades
     - Componentes UI puros
     - Hooks de lógica
     - Servicios (API, storage, etc.)
     - Tipos / modelos
[  ] Estructura de carpetas predecible
[  ] Convenciones de nombres consistentes
[  ] Sin archivos de más de 300 líneas (excepciones justificadas)
[  ] Imports absolutos (paths con alias) en vez de "../../../"


7.2 GESTIÓN DE ESTADO
[  ] Estado local para lo que pertenece a un componente
[  ] Estado global solo para lo que es genuinamente compartido
[  ] Server state separado del client state (TanStack Query, SWR)
[  ] Sin prop drilling de más de 2-3 niveles
[  ] Estado URL para lo que debe ser compartible (filtros, pestañas)


7.3 MANEJO DE ERRORES
[  ] ErrorBoundary global a nivel app
[  ] ErrorBoundary por sección crítica
[  ] Errores de red capturados y comunicados
[  ] Errores de validación distinguidos de errores de servidor
[  ] Logging de errores en producción (Sentry, Bugsnag, Rollbar)
[  ] Stack traces fuente-mapeados (sourcemaps en producción solo
     accesibles al equipo)


7.4 TIPADO
[  ] TypeScript en strict mode (si TS)
[  ] Modelos del dominio tipados
[  ] APIs tipadas end-to-end (tRPC, OpenAPI codegen, GraphQL codegen)
[  ] Sin "any" salvo justificado
[  ] noImplicitAny, noUncheckedIndexedAccess


7.5 API DESIGN
[  ] Versionado (/api/v1/...)
[  ] REST estricto o GraphQL — no mezclar sin razón
[  ] Status codes correctos (200, 201, 400, 401, 403, 404, 500)
[  ] Errores en formato consistente (JSON con estructura predecible)
[  ] Paginación estándar (cursor-based para colecciones grandes)
[  ] Rate limiting documentado
[  ] Documentación OpenAPI / Swagger pública o interna


7.6 DEPENDENCIAS
[  ] Lockfile commiteado (package-lock.json, pnpm-lock.yaml)
[  ] Auditoría regular (npm audit, Dependabot, Snyk)
[  ] Sin librerías abandonadas (último commit > 2 años)
[  ] Sin librerías de un solo mantenedor para piezas críticas
[  ] Renovate o Dependabot configurado


================================================================================
8. PERSISTENCIA Y MANEJO DE DATOS
================================================================================


8.1 GUARDADO
[  ] Auto-save cuando es viable (cada 5-10s o al perder foco)
[  ] El usuario nunca pierde lo escrito por refresh accidental
[  ] Indicador visible de "guardando" / "guardado"
[  ] Confirmación clara cuando algo se persistió
[  ] Optimistic UI con rollback en caso de error


8.2 SINCRONIZACIÓN
[  ] Multi-device sync si aplica (cuenta del usuario)
[  ] Resolución de conflictos definida (last-write-wins, CRDT, merge manual)
[  ] Indicador de "sincronizando" / "última sincronización: hace X"


8.3 OFFLINE
[  ] La app funciona (al menos en lectura) sin red
[  ] Service Worker con cache de assets críticos
[  ] Cola de operaciones pendientes que se sincronizan al volver
[  ] Indicador visible de estado offline


8.4 EXPORT E IMPORT
[  ] El usuario puede exportar SUS datos en formato estándar (JSON, CSV)
[  ] Puede importar de un backup propio
[  ] Migración de versiones del esquema documentada
[  ] Sin lock-in artificial


8.5 ELIMINACIÓN
[  ] El usuario puede borrar SUS datos completamente
[  ] La eliminación es real (no soft-delete eterno)
[  ] Plazo definido para purga (30/60/90 días tras cancelación)
[  ] Eliminación de datos también elimina copias en backups


8.6 BASE DE DATOS
[  ] Backups automáticos (al menos diarios)
[  ] Backups restaurados periódicamente (verificar que funcionan)
[  ] Indices en columnas que se filtran/ordenan frecuentemente
[  ] Migrations versionadas y reversibles
[  ] Soft deletes donde tenga sentido legal
[  ] Audit log de cambios sensibles


================================================================================
9. SEGURIDAD
================================================================================

Una brecha de seguridad puede matar el producto. Los básicos no son negociables.


9.1 TRANSPORTE
[  ] HTTPS en TODAS las páginas (sin excepciones)
[  ] HSTS header (Strict-Transport-Security)
[  ] Redirección automática de HTTP a HTTPS
[  ] Certificado válido y auto-renovado (Let's Encrypt, Cloudflare)
[  ] TLS 1.2 mínimo, idealmente 1.3


9.2 CABECERAS DE SEGURIDAD
[  ] Content-Security-Policy (CSP) bien configurada
[  ] X-Frame-Options: DENY (o usar frame-ancestors en CSP)
[  ] X-Content-Type-Options: nosniff
[  ] Referrer-Policy: strict-origin-when-cross-origin
[  ] Permissions-Policy para limitar APIs del navegador


9.3 AUTENTICACIÓN
[  ] Passwords nunca en plano (bcrypt, argon2)
[  ] Mínimo 8 caracteres + medidor de fortaleza
[  ] Soporte de password managers (autocomplete correcto)
[  ] 2FA / MFA opcional (TOTP, no SMS)
[  ] Recuperación de contraseña por email con token expiría
[  ] Bloqueo tras N intentos fallidos
[  ] OAuth (Google, GitHub, Apple) si aplica


9.4 AUTORIZACIÓN
[  ] Verificación de permisos en cada endpoint, no solo en UI
[  ] Principio de menor privilegio
[  ] Tokens de sesión seguros (httpOnly, secure, sameSite)
[  ] Tokens con expiración razonable (1-7 días, refresh aparte)
[  ] Logout invalida el token en servidor


9.5 INPUT Y OUTPUT
[  ] Validación server-side SIEMPRE (no confiar en cliente)
[  ] Sanitización de HTML para prevenir XSS
[  ] Queries parametrizadas (sin SQL injection)
[  ] Validación de tipos en todas las APIs (Zod, Joi, Yup)
[  ] Encoding correcto de output según contexto (HTML, URL, JSON)
[  ] Tamaño máximo de request body
[  ] Tamaño máximo de uploads + verificación de tipo MIME


9.6 SECRETS Y CREDENCIALES
[  ] API keys NUNCA en el cliente (mover a backend)
[  ] Variables de entorno para secrets, no hardcoded
[  ] Secrets manager en producción (Vault, AWS Secrets Manager,
     Doppler, 1Password)
[  ] Rotación periódica de secrets críticos
[  ] .env nunca commiteado
[  ] Pre-commit hook que detecta secrets (gitleaks, trufflehog)


9.7 RATE LIMITING Y ABUSE
[  ] Rate limit por IP en endpoints públicos
[  ] Rate limit por usuario autenticado
[  ] CAPTCHA en formularios de signup / login (hCaptcha, Turnstile)
[  ] Detección de bots (anti-fraud)
[  ] Bloqueo de IPs con comportamiento abusivo


9.8 DEPENDENCIAS Y VULNERABILIDADES
[  ] Auditoría automática (Dependabot, Snyk, npm audit)
[  ] CVEs críticos parcheados en menos de 7 días
[  ] No depender de librerías sin mantenimiento
[  ] SBOM (Software Bill of Materials) generado en build


9.9 ALMACENAMIENTO
[  ] Datos sensibles encriptados en reposo
